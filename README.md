# ДЗ по ClickHouse (сервис «ТАКТ»)

## Окружение и запуск

Стенд из LMS: ClickHouse 25.8.33.6 в docker compose (`стенд/`, в репозиторий не входит),
пользователь student / takt. Данные — `listening_events.csv.gz`, 10 000 000 событий,
13–26 октября 2026 UTC (первая и последняя запись: 2026-10-13 00:00:49 и
2026-10-26 23:59:59). Загружены один раз блоком первоначальной подготовки из задания.

Порядок запуска: блок первоначальной загрузки (раздел «Подготовка стенда» задания) →
`01_report.sql` → `02_order_by.sql` (сначала подготовка 2.1, потом запросы Q1–Q4 и
планы) → `03_codecs.sql` → `04_mv.sql` (подготовка, MV, заполнение истории, порции
А и Б — вставки выполнять по одному разу).

Результаты сохранены в `results/`, в заголовке каждого файла — имя запроса. В задании 2
запускал запросы не через /play, а HTTP-клиентом, поэтому показатели чтения (Read) взял
из `system.query_log` (type = QueryFinish, запросы помечены log_comment q1–q4) — задание
это разрешает, если указать источник измерений.

### 1.2 Контроль на семи событиях

Ручный расчёт: у RU в период попадают три события (19s, 20s, 21s — события
10-19 23:59:59 и 10-27 00:00:00 вне периода), короткое одно (19s) → 100·1/3 = 33.33.
У KZ два события (5s, 20s), короткое одно → 50.00.

С первого раза контроль не сошёлся: получил RU 5/3/60.00. Оказалось, при замене FROM
на values() я не перенёс условие периода WHERE, и RU посчитался по всем пяти строкам.
Добавил WHERE — результат совпал с ручным расчётом полностью
(`results/01_report_check.txt`):

```

KZ       2             1                50
RU       3             1                33.33
```

### 1.3 Ответы

1. RU: 2 771 858 событий за 20–26 октября, из них 653 114 короче 20 секунд. 23.56% —
   это примерно каждое четвёртое прослушивание: из 1000 событий в России примерно 236
   заканчиваются до 20-й секунды.
2. Это разные величины. В примере KZ доля коротких событий — 50% (1 из 2 событий), но
   оба события у одного пользователя 201, и короткое у него было, так что доля
   слушателей с хотя бы одним коротким прослушиванием — 100% (1 из 1). Событийная доля
   взвешена по активности: один пользователь с большим числом коротких прослушиваний
   сильно поднимает её, а в доле слушателей считается один раз.

## 2. Ключ сортировки и объём чтения

### 2.1 Подготовка

После блока подготовки в каждой таблице одна активная часть и 10 000 000 строк
(`results/02_prepare_check.txt`). Ключи: `hw_events_time` — ended_at,
`hw_events_country` — country, ended_at.

### 2.2 Измерения

Ответы совпали: «Германия» на обеих таблицах — DE 59423 / 14833 / 24.96; «все страны» —
одинаковые 7 строк; строка DE в общем отчёте равна отдельному отчёту по Германии.
Ответы — `results/02_answers_and_reads.txt`, планы — `results/02_plans.txt`,
показатели чтения — `results/02_reads.txt`.

| Запрос | Ключ | Granules | Прочитано строк | Прочитано байт |
|---|---|---|---|---|
| Германия | (ended_at) | 102/1221 | 835584 | 14.34 MiB |
| Германия | (country, ended_at) | 8/1221 | 65536 | 1.13 MiB |
| Все страны | (ended_at) | 102/1221 | 835584 | 14.34 MiB |
| Все страны | (country, ended_at) | 114/1221 | 931456 | 15.99 MiB |

### 2.3 Выводы

1. «Германия»: на (country, ended_at) прочитано 65536 строк и 1.13 MiB против 835584
   строк и 14.34 MiB на (ended_at) — примерно в 12.8 раза меньше. «Все страны»:
   различие маленькое и в другую сторону — 835584 (14.34 MiB) против 931456 (15.99 MiB),
   на (country, ended_at) примерно на 11% больше.
2. При (ended_at) события идут по времени, страны внутри перемешаны. Индекс отбирает
   гранулы только по ended_at — в Q1 и Q3 выбраны одни и те же 102 из 1221 гранул суток
   (в плане Condition только по ended_at), а страна фильтруется уже чтением колонок
   внутри этих гранул. При (country, ended_at) данные сгруппированы по странам, внутри
   страны — по времени. В Q2 условие ложится на обе колонки ключа (в плане country
   in ['DE','DE'] плюс диапазон ended_at) — 8 из 1221 гранул. В Q4 страны в условии нет,
   ended_at — не первая колонка ключа, но индекс всё равно работает (generic exclusion
   search): диапазон суток выбирается внутри блока каждой страны, плюс граничные
   гранулы — 114/1221, отсюда чуть большее чтение.
3. На hw_events_time «Германия» и «все страны» прочитали одинаково — 835584 строки,
   хотя подходящих событий сильно разное количество: 59423 у DE против 825369 у всех
   стран вместе. Меньше подходящих событий не значит меньше чтения: фильтра по стране
   нет в ключе, индекс выбирает гранулы суток целиком, а в них лежат все страны.
   Прочитанные строки (835584 — всё, что в выбранных гранулах), подходящие события
   (59423 — прошло фильтр по стране) и строки отчёта (1 строка DE) — три разные вещи.
4. Для запроса по Германии лучше (country, ended_at) — 1.13 MiB против 14.34 MiB; для
   отчёта по всем странам лучше (ended_at) — 14.34 против 15.99 MiB. Чтобы выбрать один
   ключ на всю нагрузку, этого мало: нужно знать, какие запросы вообще приходят (как
   часто фильтруют по стране, как часто только по времени), есть ли другие фильтры
   (пользователь, трек), что происходит с вставкой и памятью. Как показало это задание,
   ключ, выгодный одному отчёту, добавляет чтения другому.

## 3. Кодеки и порядок значений

### 3.1 Подготовка

Контроль данных: в обеих таблицах 500000 строк, 500000 уникальных event_no, от 0 до
499999, bad_rows = 0; в каждой по одной активной части Wide
(`results/03_prepare_check.txt`).

### 3.2 Соседние значения

Регулярная таблица, seconds_from_start: 0, 1, 2, 3, 4, 5.
Первые разности: +1, +1, +1, +1, +1. Вторые: 0, 0, 0, 0 — равномерный шаг.

Перемешанная: 36993; 222135; 480696; 440268; 486310; 296535.
Первые разности: +185142; +258561; −40428; +46042; −189775.
Вторые: +73419; −299989; +86470; −235817 — закономерности нет, знаки и величины
случайные.

Восстановление по вторым разностям (перемешанный фрагмент): кроме вторых разностей
нужно знать v₁ = 36993 и первую первую разность d₁ = +185142. Тогда
d₂ = d₁ + 73419 = 258561, v₂ = v₁ + d₁ = 222135, v₃ = v₂ + d₂ = 480696 — сходится
с фрагментом.

### 3.3 Размеры

`results/03_fragments_and_sizes.txt`:

```
table            column          uncompressed_bytes  compressed_bytes  compression_ratio
hw_codec_mixed   t_delta         2000000             1586160           1.26
hw_codec_mixed   t_double_delta  2000000             1962850           1.02
hw_codec_mixed   t_zstd          2000000             1543831           1.3
hw_codec_ordered t_delta         2000000             2234              895.26
hw_codec_ordered t_double_delta  2000000             2325              860.22
hw_codec_ordered t_zstd          2000000             1332284           1.5
```

### 3.4 Выводы

1. В регулярной таблице меньше всего Delta,ZSTD — 2234 байта (DoubleDelta,ZSTD почти
   столько же — 2325). В перемешанной лучший — чистый ZSTD(1): 1543831 байт.
2. Delta,ZSTD: 2234 байта против 1586160 — разница примерно в 700 раз. В регулярной
   таблице первые разности — константа +1, после Delta остаётся поток одинаковых малых
   чисел, и ZSTD дожимает его до килобайтов. В перемешанной разности — большие числа
   со случайными знаками (см. 3.2), разностное кодирование ничего не даёт.
3. Delta хранит разности соседних значений, DoubleDelta — разности разностей: при
   равномерном ряде вторые разности почти нулевые и хранить почти нечего. ZSTD после
   них дожимает оставшуюся избыточность. Дополнительное преобразование не гарантирует
   меньший размер: на перемешанном ряду разности — шум, DoubleDelta ещё и платит
   служебные биты за знаки и обрывы серий, и итог (1962850) выходит хуже даже чистого
   ZSTD (1543831).
4. Порядок хранения нельзя выбирать только по сжатию: ORDER BY определяет, как работает
   первичный индекс, то есть сколько читают запросы. В задании 2 ключ по стране выиграл
   у запроса по Германии и проиграл отчёту по всем странам. Переставить строки ради
   сжатия одной колонки — значит сломать отсечение гранул по фильтрам.

Про сохранение информации: кодеки сжимают без потерь, значения времён восстанавливаются
точно, поэтому события за любой интервал, например 10:15–10:45, считаются точно. Если
хранить только дневные количества, всё внутри дня теряется: из дневного счётчика
нельзя получить данные за часть дня. Агрегат хранит ровно то, что в него положили.

## 4. Материализованное представление

### 4.1

Источник до опыта — 10000000 событий. MV создан, target сразу после создания — 0 строк
(`results/04_1_source_and_mv.txt`): инкрементальное MV обрабатывает только новые
вставки, уже лежавшую историю оно не трогает.

### 4.2

Общий контроль (запрос из задания) — 0 строк расхождений на всех трёх этапах: после
заполнения истории, после А и после Б (`results/04_2_3_history_A.txt`,
`results/04_4_portion_B.txt`).

### 4.3 Порция А

Ручный расчёт: 19:00 RU — 4 события, коротких 2 (5 и 19; 20 и 40 не проходят),
сумма 5+19+20+40 = 84 → 50.00%, средняя 21.00. 19:00 KZ — 1 событие (25), коротких 0 →
0.00%, средняя 25.00. Фактический отчёт совпал полностью:

```
hour                 country  events_count  short_count  seconds_sum  under_20_percent  avg_seconds
2026-10-27 19:00:00  KZ       1             0            25           0                 25
2026-10-27 19:00:00  RU       4             2            84           50                21
```

### 4.4 Порция Б

Историческая группа RU 24 октября 12:00 до Б: 26478 / 6655 / 3659184 (25.13 / 138.2).
После Б: 26479 / 6656 / 3659191 (25.14 / 138.19) — ровно +1 событие, +1 короткое,
+7 секунд, как и должно быть от опоздавшего события 12:34 на 7 секунд.

Отчёт после Б:

```
hour                 country  events_count  short_count  seconds_sum  under_20_percent  avg_seconds
2026-10-27 19:00:00  KZ       1             0            25           0                 25
2026-10-27 19:00:00  RU       5             3            85           60                17
2026-10-27 20:00:00  RU       1             1            10           100               10
```

Ручный расчёт совпал: у 19:00 RU добавилось событие в 1 секунду (5 событий, 3 коротких,
85 секунд → 60.00% и 17.00), у 20:00 RU одно событие на 10 секунд (100.00% и 10.00).
Источник после опыта — 10000008 событий.

### 4.5 Ответы

1. При порции Б MV обработало вставленный блок из трёх строк: два события 27 октября
   ушли в часы 19:00 и 20:00, а событие с временем 24 октября 12:34 попало по своему
   toStartOfHour в старую группу «24 октября 12:00 RU» и изменило её итог. MV
   группирует по времени события, а не по времени вставки. Историю пришлось заполнять
   отдельно, потому что MV видит только новые блоки после создания — 10 млн уже
   лежавших событий оно не обработало (target был пустой, мы это зафиксировали).
2. SummingMergeTree складывает строки одной группы при слияниях, а слияния происходят
   в фоне и не сразу. Пока слияния не было, одна логическая группа разложена на
   несколько физических строк (историческая вставка + строки от MV), поэтому при чтении
   нужен GROUP BY (hour, country) с sum — тогда ответ правильный в любой момент. Контроль
   после вставок сразу показывал 0 расхождений, то есть так и есть.
3. RU 19:00 после Б: правильные значения — 5 событий, 3 коротких, 85 секунд →
   100·3/5 = 60.00% и 85/5 = 17.00. Если усреднять по порциям: проценты (50 и 100)
   дали бы 75.00, средние (21 и 1) — 11. Оба ответа неверные, потому что порции
   разного размера (4 и 1 событие). Считать надо по суммам показателей, а не по
   среднему от средних.
4. Пересчитать долю с порогом <10 только по target нельзя: там лежит countIf для
   порога 20 и сумма секунд, а распределение длительностей внутри групп потеряно —
   сколько было событий короче 10 секунд, из этих чисел неизвестно. Для нового порога
   нужны сырые события или дополнительные счётчики по бакетам длительности в target.
